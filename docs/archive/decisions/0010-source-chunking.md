## 1. 已确认的边界

1. 每个 chunk 是一个**预定 cue**，后续允许重新切分、合并或移动边界；不是最终发布字幕。
2. chunking 不产生显示换行、不尝试用两行容量容纳长文本；超过一行的逻辑字符预算就考虑切 cue。
   字体、像素、视觉换行全部归 rendering。字符数达标不代表实际画面一定放得下。
3. **按用户最新确认，英文容量采用42字符、CPS采用20，不再放宽Netflix指标。**
4. 本阶段**完全不借时间**：不预支 gap，不延长 end，不提前 start，不收拢字幕间隙。
   两轮分组完成后可只读计算预算，不修改时间或反向影响裁切/合并；后处理另行决定实际借时间。
5. 英文词、顺序、词 ID 和声学时间保持；不删口语词、不改写英文。
   初次 chunking 使用本地Stanza成分句法，不调用LLM；不能改英文来满足预算。
6. chunking 用例不调用 ASR/transcription；完整集成会重新运行上游。不沿用中文优先或中英比例分配，也不在本 ADR 新增模块。
7. **仅容量>42字符或基本时长>7000ms触发第一轮裁切；CPS超20不触发裁切。**
8. **2026-11-01用户确认：预算无解时保留完整候选及问题，交后处理，不视为指标通过。**
   这只适用于容量/时长/CPS与语块保护的冲突，不把丢词、重复、输入损坏等正确性错误降级。
9. 第二轮仅处理超短块；**合并后的CPS必须≤20，超过就放弃该合并方案**，并可尝试另一侧。
10. **2026-11-02用户确认：源语chunking属于现有`srt_processing`的独立用例。**
    transcription仍负责完整句子及词时间；不将字幕预算反向写入转录句界，也不为该阶段新增功能模块。
11. 用户采纳裁切择优、单邻居合并及最终并前的建议。跨原句合并采用**原始句间gap<500ms**，
    依据本轮未找到可直接采用的行业上限后的用户指定回退政策；不是Netflix规定。

“42字符预算”指**整个英文 chunk 最多42字符**，不是两行共84字符。
rendering 即使后来视觉换行，也不能反向让 chunking 获得第二行的额外容量。

### 2.1 指标集中存放，不散落魔法数

未来实现使用`srt_processing`内单一、版本化的规则常量文件，候选路径为
`src/srt_processing/domain/chunking_policy.py`；本轮不创建生产文件。常量内容为：

```python
ENGLISH_MAX_CHARACTERS = 42
ENGLISH_CPS_LIMIT = 20
MIN_CHUNK_DURATION_MS = 834
MAX_CHUNK_DURATION_MS = 7000
CROSS_SENTENCE_MERGE_GAP_LIMIT_MS = 500  # 严格小于；这是项目规则，不是Netflix指标
```

分割、合并、报告及验证使用同一规则来源，不各存一套值；跨模块通过公开契约传递政策身份，
不跨功能模块导入私有常量文件。政策版本及实际值进入工件/缓存身份，不原地改变旧profile含义。

### 2.2 计数与基本窗口

Netflix明确将空格和标点计入字符数及阅读速度；本稿计数也包含二者。
[官方计数说明](https://partnerhelp.netflixstudios.com/hc/en-us/articles/115001352212-How-is-reading-speed-measured-Do-punctuation-and-spaces-count)。
项目拟明确用权威英文正文投影的 Unicode 码点数计数；不计算换行、样式标签或辅助标记，
也不以字体像素宽度或中文半宽单位计英文字符。码点口径是项目实现约定，不冒称官方定义了所有 Unicode 细节。

基本窗口及指标为：

```text
start_ms = 首个源词.start_ms
base_end_ms = 最后一个源词.end_ms
base_duration_ms = base_end_ms - start_ms
english_CPS = 1000 × english_character_count / base_duration_ms
```

跨词内部的空档自然在基本窗口内，但不增加最后一个词之后的显示时间。
本阶段报告的是**基本窗口指标**，不是最终显示指标；后处理改分块或排时后必须重新验证。
最终帧投影另行负责，不能把“20帧”不分帧率地写成统一最短时长。

资料差异：官方时间指南另有“20 frames (or 4/5 sec)”表述，与其24fps语境及通用要求不完全一致。
本稿明确采用通用要求及模板指南一致的5/6秒，不静默混用800ms。
[官方时间指南§3](https://partnerhelp.netflixstudios.com/hc/en-us/articles/360051554394-Timed-Text-Style-Guide-Subtitle-Timing-Guidelines)。

## 3. 两轮处理：先逐句裁切，再遍历chunk处理超短

输入是句界恢复后的完整英文句子及其word IDs、词级时间，而不是只有句子字符串。
首轮按源顺序遍历原句；第二轮遍历第一轮的输出chunk序列，包含新拆出的子块。

### 3.1 第一轮：容量或时长超长才分析、尝试裁切

```text
对每个原始句子：
    若字符数>42 或 基本时长>7000ms：
        句法分析 → 生成合法切点 → 尝试分割 → 保存子chunks及未解问题
    否则：
        原样保留为一个chunk，不为CPS超标调用句法模型或裁切
    对所有输出chunk：
        基本时长<834ms则标记超短；CPS>20则记录超标问题
```

四项全部达标的原句原样保留。只有CPS超标的原句也不裁切，但不能标为全部指标通过。
同一句若既超容量又超短，先进入裁切分支；原句和新拆子块的超短问题均交第二轮。
句法模型及已接受的择优方向见下文；其具体跨度识别和稳定比较规则需在实现设计中冻结。

裁切只解决可解决的容量/时长问题，不以CPS优化为裁切目标，不强制所有分割方案满足20 CPS。
不存在合法切法时保留完整候选及问题，不伪造时间、删词或循环强拆。

多个裁切方案之间：不破坏保护范围，优先选择所有子块均满足42字符/7秒的方案，
再比较句法完整性及不必要的切换；不为改善CPS或超短而额外裁切。具体句法标签/比较口径须以用例固定，
不增加跨句全局优化，也不把“Stanza给出树”当作已经选定唯一切法。

可选边界及保护范围：

- 以 transcription 已有完整句子提供句法分析上下文；不让句法模型重新决定 canonical 句界。
- 优先考虑从句结束、合适标点之后、并列/从属从句之前的词间位置；连词和介词不是见到就切。
- 不切单词内部；保护已确认的专名/术语跨度，以及模型识别出的冠词＋名词核心、形容词＋名词、
  介词＋宾语、姓＋名、助动词/否定词＋动词等紧密组合。
- 不把整棵任意长NP都设成不可拆：带关系从句的长名词短语仍可能在其内部完整从句边界切分。
  具体保护跨度和边界规则应在实现前用例明确，不能以笼统“句法正确”代替规则。
- 不仅凭逗号切数字，也不把 `Coca-Cola and Gillette` 中的and自动视为从句边界。

Netflix模板指南要求跨cue分段考虑从句及语法断行原则；但自动识别正确边界是本项目工程责任，
不是规范保证。[模板指南§25](https://partnerhelp.netflixstudios.com/hc/en-us/articles/219375728-Timed-Text-Style-Guide-Subtitle-Templates)。

“绝不切断”可对**已识别/已确认的保护跨度**机械执行；模型仍可能漏识别或误识别。
若不可分语块本身超过42字符或7秒，应报告冲突，不偷偷删词、借时间或强拆成假合格结果。

### 3.2 第二轮：仅对超短块尝试相邻合并

从左到右遍历第一轮的chunk序列。遇到基本时长<834ms的块，分别检查与当前前、后邻居的
合并方案；先过滤不合法的方案，再在合格方案之间择优。合并后更新序列，不再回到第一轮裁切。

合并结果必须同时满足：

- 字符数≤42；
- CPS≤20，超过就放弃该方案；
- 基本时长≤7000ms且≥834ms。

此外还须满足合并边界：

- 不跨section或不同已知speaker；null不等于确认同一人，不允许通过null桥接两个不同已知speaker。
- 跨原句时，所跨原始句界的gap必须小于500ms；这个阈值是项目政策，不是Netflix规定。
  gap以左句末词end与右句首词start计算；499ms允许、500ms及以上拒绝，负值属于时间轴错误。
  同一句内的相邻块不因此额外套用跨句上限；仍须满足四项合并指标及全部保护关系。
- 只合并连续源词覆盖，不破坏保护关系；计算合并窗口仍按首末源词取时间，不移动词或借用末词后空档。

合法候选的择向顺序：

1. 优先两个块均来自同一个原始句子的方案；
2. 同级候选优先选择原始word时间计算出的合并gap更短的一侧；
3. 仍相同时固定优先并前。

前一个方案即使同句或gap更短，只要合并后CPS>20，也必须先淘汰，不能靠优先级绕过指标。
同句判定依据完整source sentence归属，不把跨多个原句的复合块因共享一个sentence ID就算同句。
两个方向均无合格方案则保留原块及超短问题，交后处理；不把不足834ms的中间合并结果当作合格结果。
每次只考察前/后一个当前邻居，不搜索三个或更多块一起才能达标的组合；这种未解情况留后处理。
当前邻居可以是此前已合法合并形成的块，但不能先接受一个未达834ms的中间结果，再继续凑时长。
连续短块的遍历更新须以实例冻结，不隐含全局最优承诺。

### 3.3 CPS只报告或阻止合并，不驱动裁切

例如一个40字符、1秒的原句只有CPS超标，第一轮直接保留并报告40 CPS，不调用句法模型拆分。
这不表示放宽20 CPS标准，而是将其保留给后处理。两个短块若合并后为42字符/1.5秒＝28 CPS，
即使容量和时长均满足，也放弃该合并方案。

类似地，独立的 `Yes.` 若只有300ms、又不能合法合并，不能在本阶段伪造834ms。
按用户确认，保留原始300ms候选并明确标为待后处理，不伪报最短时长通过。
本阶段不执行字幕间隙调整、镜头吸附或end延长；只读预算见第3.5节。

### 3.4 跨句gap上限的行业核查：2026-11-02

本轮针对Netflix及前次调研项目的相关规范/源码复核，区分“cue合并资格”与“延长字幕或ASR聚合”：

| 资料及具体位置 | 核对到的规则 | 是否直接作为本项目跨句cue合并上限 |
|---|---|---|
| [Netflix时间指南§5–6](https://partnerhelp.netflixstudios.com/hc/en-us/articles/360051554394-Timed-Text-Style-Guide-Subtitle-Timing-Guidelines) | 半秒用于短gap收拢；鼓励合并相邻字幕平衡阅读速度，但没有给出统一跨句合并gap上限 | 否；不能把半秒收拢条件冒称合并上限 |
| [VideoLingo `align_timestamp`](https://github.com/Huanshere/VideoLingo/blob/main/core/_6_gen_sub.py) | `0 < delta_time < 1`时将上一条end延到下一条start；没有在此合并两条正文 | 否；这是1秒内延时，违反本阶段不借时间的边界 |
| [VideoLingo `split_by_mark`](https://github.com/Huanshere/VideoLingo/blob/main/core/spacy_utils/split_by_mark.py) | 按破折号/省略号等文本条件连接片段，不使用源词gap决定合并 | 否；不是可引用的毫秒上限，也不照搬其标点解释 |
| [pyVideoTrans `BaseRecogn._post_fix`](https://github.com/jianchang512/pyvideotrans/blob/main/videotrans/recognition/_base.py) | 有零时长文本并入上一条的分支；没有给出本任务的非零短cue跨句gap上限 | 否；零时长补救不能替代我们的合法源词窗口策略 |
| [AppTek 2025 §2.3](https://aclanthology.org/2025.iwslt-1.21.pdf) | ≥3秒停顿用于分句，再逐句进行字幕分段 | 否；分句阈值不是对既有完整句子的合并资格 |
| [FBK 2026 §2.4](https://aclanthology.org/2026.iwslt-1.7.pdf) | 音频VAD片段为ASR聚合时选择10秒gap，聚合时长上限600秒 | 否；对象和目标是ASR输入，不是≤7秒字幕cue |

结论限定为：**在本轮核对的资料中，没有找到可直接采用的跨句短cue合并gap上限**，
不是断言所有行业方案都没有。按用户指定，使用500ms作为本项目上限，沿用草案的严格`gap<500ms`语义。
它与Netflix的半秒规则数值相同，但来源和用途不同；不得标为“Netflix规定500ms内才能跨句合并”。
GitHub源码为本次阅读的main，未取得固定commit SHA；未克隆、运行外部项目或复现实验。

### 3.5 两轮分组后的只读阅读预算

由 `srt_processing` 在两轮分组后计算，不新增模块。固定首词start与末词end，只估算可向后延长的上界：

```text
D = 末词end − 首词start
B = max(0, min(500ms, 7000ms − D, 媒体结束 − 末词end,
               下一源词开始 − 末词end − 预留间隔))
```

末条无下一源词时省略该项。采用现有 ASR 对齐词时间，不另要求静音证明；预留间隔及
缺帧时的保守估算与 ADR-0012 一致。必要数据缺失不视作无限可借。
500ms是独立的预算延长参数，不是跨原句合并的 `gap<500ms` 门槛。基础窗口违规或已知边界冲突仍须报告，
不能因 `B=0` 当作通过。

按[Netflix成人简中9 CPS](https://partnerhelp.netflixstudios.com/hc/en-us/articles/215986007-Chinese-Simplified-Timed-Text-Style-Guide)
分别提供原始窗和最大窗的中文阅读预算。纯汉字示例分别为 `floor(9 × D / 1000)` 与
`floor(9 × (D+B) / 1000)`；混排使用同一版本化计数规则。1秒窗口若可借满500ms，预算由9字变为13字。
排版容量独立提供；不把现有16单位软目标升级为硬上限，也不为达预算删减原意。
后处理改分组或排时时重新计算并校验；预算不是已分配时长，也不代表英文CPS或最小时长已经通过。

## 5. 模块归属、最小输入/输出与相关ADR边界

### 5.1 已确认归属，尚未实施

`srt_processing`提供独立的源语chunking用例，读取transcription的公开产物，发布自己的候选
chunk工件、报告和复用身份，不修改`source_alignment.json`，也不复用最终双语plan的完成标记。
模块中既可有翻译前的源语规划用例，也可有翻译后的字幕验证/导出用例；模块不是流水线步骤编号。

```text
transcription：完整英文句子＋词时间
    → srt_processing：源语chunking
    → translation及后处理（具体契约/归属另议）
    → 最终字幕验证与导出
    → subtitle_rendering
```

orchestration负责组装阶段顺序和公开工件依赖，不负责切分规则；功能模块不得互相调用私有实现。
本ADR不借归属决定提前接受ADR-0008的具体composition/import方案。
公共工件契约归`archive_core`；chunking独立输入/输出、manifest及缓存身份在实施前评审。
translation目前仅消费完整句子，后续接入候选chunks需要单独调整公开输入契约，不能假设已经支持。

这是对原ADR-0003“字幕模块只在整句翻译后工作、不为翻译准备单元”的**已接受职责扩展设计**，
尚未实施；当前代码仍为旧契约与v3，实施时直接替换，不保留旧执行路径；历史验收记录保留。

### 5.2 最小输入/输出

输入：已验证的canonical英文词/句子/时间、可选section/speaker、已确认名称跨度，以及版本化

## 6. 代价与不可同时保证的要求

- 每chunk只给42字符预算，会比允许2×42更容易产生较多、较短的块。
- 原词/时间不变、不借时间、保护语块、42字符、834ms下限及CPS上限，并非对任意讲话都存在共同解。
- CPS不触发裁切但限制合并是已确认的非对称政策：可保留原有超CPS候选，不能接受超CPS合并结果。
- 两轮局部处理简化实现，但不会消除多个合法切点/合并方向，也不保证全局最优。
- 基本时长超过7秒应尝试切，但长单词/不可分组等情况下可能只能交审；不能截掉发音以缩短到7秒。
- 句法保护不是跨语义对应证明；本阶段通过不代表翻译、双语同步、像素或最终显示质量通过。
